Goal (user, 2026-11-08): 'see if our app can totally replace what Synapse does ... looking forward to delete Synapse fully'.

What Synapse 4.0.896 does for the Viper (from its logs in %LOCALAPPDATA%\Razer\RazerAppEngine\User Data\Logs: background-manager4.log connectedDevices JSON, profiles.log, lighting-engine4.log, macro.log):
- One profile '<PC-NAME>-Default'. DPI stages 400/800/1800/2400/3200, active 5, polling 1000: identical to what the mouse itself stores (set-mouse reads them from the mouse).
- Button mappings: [] (none). Macros: none. dkmKeys are factory (Button4, Button5, DPI cycle-up).
- Lighting: logo LED, quick effect 'spectrumCycling' (uiEffectId 3, applied again 2026-11-08 10:51), brightness 70, no idle-off. This is the only thing Synapse actively does for the user.
- Also running: 9 RazerAppEngine processes, Razer Game Manager Service 3 (auto), Razer Elevation Service, drivers RzCommon + RzDev_0078 (PID0078Drv/RzComDriver from Synapse 3, uninstallers in C:\ProgramData\Razer\Synapse3\Uninstall). It polls the mouse, which causes px-wfee.
- Only Synapse can do Viper firmware updates (currently 1.04).

Plan:
1. Reversible trial: quit Synapse, disable its autostart and the Razer services, replug the Viper. Check set-mouse (DPI/polling unchanged) and note what the logo does (spectrum cycling is Razer's factory default, so it may look the same; brightness 70 may not persist). RawAccel is unaffected: the Viper uses profiles[0] 'default', which applies to any unlisted device id.
2. If fine: uninstall Synapse (Settings > Apps), then PID0078Drv and RzComDriver with their uninstallers, then check that Game Manager Service 3 is gone. Re-verify set-mouse reads the Viper over plain Windows HID and the rotation still applies.
3. Optional, user decides: Viper lighting in set-mouse/portal (off / static colour / spectrum / brightness) via OpenRazer's protocol. Check the Viper's LED id and effect commands in the OpenRazer source first. Related: px-hkts (writable DPI/polling).
